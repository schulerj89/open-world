# v1.3.0 Settlement Contracts Direction

Status: accepted for v1.3.0

## Scope

This decision covers the next purpose pass for Aeolian Wilds: procedural hamlets, small buildings, settlement-linked contracts, visible memory spend, and a more upbeat adventure music direction. It does not choose combat, inventory, crafting, dialogue trees, save files, multiplayer, imported town art, or a major renderer change.

The current project already has the right foundation:

- Deterministic endless terrain from world `x,z` plus seed.
- Chunk streaming at `TERRAIN_RADIUS = 4` with disposal outside the keep radius.
- v1.2 `CHUNK_SEGMENTS = 24`, water rejection, weather, and the three-beacon objective loop.
- `EnvironmentSystem` instanced rocks, flowers, waystones, crystals, and ruin fragments.
- Debug snapshots with FPS, chunks, render calls, triangles, resource counts, heap, terrain/environment/water memory estimates, weather, objective state, and player position.
- Verification through `npm run build`, `npm test`, `npm run test:smoke`, and `npm run capture:screenshots`.

## Version Recommendation

Ship this as `1.3.0`, a minor release.

Settlements and contracts create a new gameplay loop, but they should extend existing systems instead of changing the project contract. The world remains a deterministic low-poly Three.js exploration game, the renderer stays WebGL, the terrain radius stays fixed, and the existing objective/debug/smoke structure remains valid.

Reserve a major version for a change that rewrites the game promise: combat, persistent inventory/economy, authored campaign progression, imported asset pipeline, save migration, multiplayer, or a renderer baseline change.

## Decision

Choose one core mechanic: settlement contracts.

The player finds a small hamlet, triggers a local repair request near its center sign or well, completes one settlement need, and returns to the hamlet for a visible before/after improvement. The rule is simple: help this place. The iteration space is deep enough for future versions because contracts can vary by biome, weather, nearby terrain, building role, route shape, reward presentation, and settlement state without adding a generic waypoint chain.

For v1.3.0, implement one contract type:

- `Stabilize Hamlet`: each generated hamlet has one local repair need.
- Entering the hamlet starts the contract and marks three nearby local resource nodes.
- Resource nodes are deterministic terrain candidates around the settlement and use the settlement biome to choose timber, stone, or crystal.
- Collecting all resources and returning to the hamlet changes the settlement presentation with a completed repair marker.

This is settlement-linked rather than long-distance waypointing. The hamlet is the source, context, return point, and proof of impact.

## Procedural Hamlet Contract

Generate hamlets as deterministic settlement anchors sampled from chunk coordinates and world seed.

Site selection:

- Consider one settlement candidate per coarse cell, not every chunk, so towns remain rare.
- Reject underwater, steep, high-snow, and cramped sites with `heightAt`, `slopeAt`, `moistureAt`, biome classification, and `SEA_LEVEL`.
- Prefer flat dry benches near biome edges, shore approaches, low ridges, or clearings because these give readable arrival silhouettes.
- Keep settlement placement pure from world coordinates and seed. Do not introduce saved placement maps.

Layout grammar:

- Start with a central sign, well, or weather vane.
- Place 3 to 7 small buildings around it using a deterministic radial or lane grammar.
- Use reusable low-poly building modules: foundation, wall box, roof prism, chimney, awning, fence, crate, lantern, and path marker.
- Rotate buildings toward the center or the nearest generated lane.
- Local paths remain future work. Do not carve terrain in v1.3.0.
- Keep collision proxies simple: board/vane/buildings can use coarse boxes or circles; decorative props remain nonblocking.

Rendering fit:

- Reuse the `EnvironmentSystem` pattern: ring-level `InstancedMesh` batches by building part, material, and LOD band.
- Use shared geometries and vertex/instance color variation rather than per-building materials.
- Generate and cache compact settlement plans for active or near-active settlement cells, then fill instanced batches when the loaded chunk signature changes.
- Cull hamlet detail outside the visible ring; keep a cheap distant marker or silhouette only if it helps navigation.

This fits the current systems because settlements are just a higher-order deterministic placement layer over the same terrain, biome, chunk, instancing, fog, and debug contracts.

## Purpose

Settlement contracts give Aeolian Wilds a clear player sentence: explore the wilds to help small weather-battered communities recover.

The loop creates purpose without needing combat or inventory:

- A hamlet gives the player a reason to care about a location.
- The surrounding terrain becomes a local problem space, not just scenery.
- Completion creates an immediate visible change in the world.
- Future versions can connect hamlets into routes, reputation, music layers, NPC presence, and larger settlement states while preserving the same simple contract verb.

## Game Inspirations

- `The Witcher 3: Wild Hunt`: notice boards make settlements feel like local quest sources. Use the board readability and local stakes, not the content structure.
- `Monster Hunter`: a hub frames repeatable contracts clearly before the player enters the field. Use the clean contract loop, not hunting or gear grind.
- `Death Stranding`: routes matter because terrain and delivery context are visible. Use terrain readability and return payoff, not long-distance traversal as the whole mechanic.
- `The Legend of Zelda: Breath of the Wild`: distant silhouettes and weather make destinations legible. Use visible landmarks and hilltop reveals, not physics sandbox scope.
- `A Short Hike`: compact local goals turn movement into relaxed exploration. Use short readable objective arcs.
- `Minecraft`: villages are readable through simple building silhouettes and repeated modules. Use procedural settlement language, not block construction.
- `Dragon Quest Builders 2`: towns improve visibly after player help. Use before/after settlement feedback, not crafting systems.

## Music Direction

Replace the current exploration feel with a brighter upbeat adventure theme for v1.3.0, especially near settlements. The target is warm, melodic, and optimistic: plucked strings, light percussion, simple folk lead, and a loop that supports motion without sounding like combat.

Acceptance requirements for any selected track:

- License is explicitly compatible with the project and captured in the README or asset metadata.
- Track loops cleanly for at least 90 seconds of play.
- `M` mute remains instant.
- Settlement completion can trigger a short sting or mix change without restarting the whole track.

## Performance And Memory Guardrails

Use more memory visibly, but keep the existing performance contract.

Hard limits:

- Visible-browser target: 60 FPS.
- Chromium headless smoke floor: greater than 45 FPS.
- JS heap: under 100 MB when `performance.memory` is available.
- Render calls: under 170 after settlements.
- Triangles: under 220k for the default camera and terrain radius.
- Geometries: under 140.
- Textures: under 16.
- Chunk build time: under 12 ms in smoke.

Working targets:

- Keep `TERRAIN_RADIUS = 4`; spend memory on visible settlement detail instead of farther terrain.
- Raise `CHUNK_SEGMENTS` from 24 to 32 and verify terrain geometry remains below 8 MB.
- Target settlement instance buffers under 4 MB.
- Target building/module draw calls at 10 to 18, hard stop at 28.
- Target settlement triangles under 45k in the default visible ring.
- Keep settlement sync under 4 ms when the loaded chunk signature changes.
- Avoid realtime shadows, transparent building materials, per-frame matrix rewrites, per-building meshes, and per-building textures.
- Add memory that the player can see: more building modules, signs, lamps, fences, repaired-state props, and local path markers. Do not spend it on invisible caches or distant terrain radius.

## Debug Hooks

Extend `window.__OPEN_WORLD_DEBUG__.getSnapshot()` with settlement and contract fields:

- Active settlement count and nearest settlement id.
- Settlement state: undiscovered, available, accepted, completed.
- Active contract title, step count, completed steps, target distance, and return-required flag.
- Building instance counts by family.
- Settlement instance buffer MB and cached plan MB.
- Settlement sync time.
- Any placement rejection or asset/procedural generation errors.

Add debug helpers if practical:

- Force nearest settlement discovered.
- Accept/complete/reset the current contract.
- Teleport to nearest settlement and active contract target.
- Toggle settlement debug markers.

## Acceptance Checks

Implementation is accepted when these pass:

- `npm run build`
- `npm test`
- `npm run test:smoke`
- `npm run capture:screenshots`

Unit coverage:

- Settlement placement is deterministic for the same seed and cell.
- Candidate rejection prevents underwater, steep, and unplayable settlement anchors.
- Building layout stays stable when loaded chunk order changes.
- Contract targets are reachable from the settlement and remain above `SEA_LEVEL + WATER_BLOCK_MARGIN`.
- Completed settlement state changes deterministically.

Smoke coverage:

- The default world streams with at least one reachable settlement candidate or a debug teleport to one.
- Accepting a contract exposes target progress through the debug snapshot.
- Completing target steps and returning to the hamlet marks the contract complete.
- Calls, triangles, geometries, textures, heap, chunk build time, and FPS stay inside hard limits.
- Console and page errors remain empty.

Screenshot coverage under `artifacts/screenshots/v1.3.0/`:

- `01-title.png`: title still clean.
- `02-world-debug.png`: default world with debug overlay.
- `03-settlement-arrival.png`: hamlet readable from gameplay camera distance.
- `04-contract-board.png`: accepted contract state visible without UI overlap.

- `06-settlement-complete.png`: completed hamlet before/after change visible.
- `07-night-or-weather-settlement.png`: lamps, weather tint, or storm readability near buildings.

Visual QA:

- Buildings do not float, sink, z-fight, or spawn in water.
- The player remains visible near buildings, fences, paths, and props.
- Hamlet silhouettes read before individual props.
- Debug overlay text remains readable.
- Settlement materials remain coherent with the low-poly terrain, weather, water, and sky.
